Система работы с задачами

Связное описание того, как задача проходит путь от идеи до проверенного результата без потерь по дороге, и минимальный код, чтобы завести это у себя — без привязки к конкретному трекеру и без чужих ключей доступа.

1Коротко: путь одной задачи

Чтобы за минуту увидеть весь путь целиком, прежде чем читать про каждое правило по отдельности.

Два шага делает человек, остальные пять идёт механизм сам. Пропущенный шаг — не сокращение пути, а дыра, в которую проваливается задача.

Что происходит на каждом шаге

  • 01. Задача. Кто-то заметил проблему или идею — словами, в разговоре, в баг-репорте.
  • 02. Тикет-ТЗ. Задача переписана в тело тикета так, чтобы её можно было выполнить, не спрашивая автора ничего дополнительно.
  • 03. Одна команда поднимает работу. Свежая копия кода от главной ветки, ветка с номером задачи, исполнитель получает бриф из тела тикета. Одна команда — не десять ручных шагов, которые кто-то забудет повторить одинаково.
  • 04. Сторож следит. Простой процесс проверяет: работа ещё идёт или встала — и подаёт голос, если работа зависла или отчиталась о готовности.
  • 05. Независимая приёмка. Проверяет НЕ тот, кто делал. Сверяет результат с признаком закрытия из тикета, а не с собственным впечатлением «выглядит нормально».
  • 06. Гейт и вливание. Перед тем как результат попадёт в общую ветку — прогон тестов и сканер секретов. Не прошло — не вливается, независимо от вердикта приёмки.
  • 07. Уборка. Отработавшая копия кода и её процессы убираются — иначе они тихо копятся и однажды кладут машину.

2Три правила пайплайна

Это три коротких правила, на которых держится всё остальное — нарушь любое одно, и весь пайплайн перестаёт работать, даже если код в нём безупречен.

1. Тикет — самодостаточное ТЗ
Исполнитель читает ТЕЛО задачи, а не историю переписки вокруг неё. Если контекст важен для результата — он переносится в тело тикета текстом. Не перенесённый контекст для исполнителя не существует.
2. Проверяет не тот, кто делал
Независимая приёмка — это ДРУГОЙ человек или другой прогон, не участвовавший в реализации. Автор решения систематически не видит своих слепых пятен — не потому что невнимателен, а потому что уже уверен в своём решении.
3. Закрытие — только по проверенному факту
Признак закрытия — это команда и её вывод, а не заявление «готово». Намерение сделать — не то же самое, что сделанное и проверенное.

3Цикл пакетами и границы полномочий

Чтобы поток мелких задач не перескакивал с темы на тему и не утопил того, кто принимает решения, в десятках мелких вопросов по одному.

Шесть шагов, по кругу:

  • Накопление. Всё, что появилось — задача, находка, идея — ложится номером в один список. Ничего не стартует само по себе.
  • Пакет. Тот, кто отвечает за результат, называет номера задач, которые берутся в работу прямо сейчас. Порядок работ ВНУТРИ пакета выбирает исполнитель — это уже не его забота.
  • Разбор до кода. Сначала факты: как это работает сейчас, где развилка. На этом шаге ещё ничего не чинится.
  • Лист развилок — один раз на пакет. Все вопросы, которые требуют решения сверху, задаются ОДНИМ списком, а не по одному: суть в двух строках, варианты, рекомендация исполнителя.
  • Производство без остановок. Реализация, тесты, проверка — без промежуточных согласований. Вопрос, возникший по ходу, не прерывает работу — ложится в лист развилок СЛЕДУЮЩЕГО пакета.
  • Приёмка одним заходом. Что сделано и чем проверено · что не вышло и почему · лист развилок для следующего пакета.

Правило «касаний ровно три за пакет»: назвал пакет → ответил на лист развилок → принял результат. Всё остальное — зона того, кто выполняет работу.

Что решает только тот, кто отвечает за результат целиком: новый механизм, которого раньше не было · необратимые действия · деньги · состав следующего пакета · всё, что физически может сделать только человек (пароль, код подтверждения, оплата). Всё остальное — технический путь, порядок работ, починка очевидного дефекта — решается без него.

4Тикет — единственный список задач

Устная договорённость исчезает вместе с разговором, в котором её произнесли; второй список задач неизбежно разойдётся с первым, и тогда неизвестно, какому верить.

Правило одно и жёсткое: решение, не попавшее в трекер, не существует.

Каждая задача заводится под своей темой (эпиком/проектом) — задача-сирота без темы теряется в общем списке первой.

В тело задачи обязано попасть: решение того, кто отвечает за результат, — дословно, а не пересказом · факт с источником (лог, команда и её вывод), а не формулировка «вроде починили» · что сделано и чем именно проверено · что отложено и по какой причине.

В тело задачи НЕ идёт: промежуточные шаги и рассуждения по ходу · диагностика без последствий · статусы «ещё работаю» — трекер, куда пишут всё подряд, очень быстро перестают читать целиком, и тогда важное тонет вместе с шумом.

Решение стоит пометить машинно — скрытой меткой с датой прямо в теле тикета (например строкой вида <!-- решение: 2026-01-01 -->), чтобы следующий заход по этой же задаче не переспрашивал уже решённое.

Тикет пишется как самодостаточное ТЗ: исполнитель читает ТОЛЬКО тело задачи, не переписку вокруг неё (правило 1 из раздела выше).

Если трекера нет вовсе

Трекер с API. Подойдёт почти любой — вплоть до бесплатных GitHub Issues или GitLab Issues: главное, чтобы задачу можно было прочитать и закрыть командой, а не только руками через веб-страницу.

Один-единственный список задач. Если трекера действительно нет — подойдёт даже один markdown-файл в репозитории, где каждая задача — отдельный заголовок с номером. Важно, чтобы список был ровно один: второй список («ещё где-то в переписке», «в отдельном файле на память») неизбежно разойдётся с первым.

Цена опроса трекера

У трекера есть общий лимит запросов

Лимит запросов в час делится на ВЕСЬ аккаунт — его тратят одновременно все, кто к трекеру обращается: сторож, приёмка, ручные проверки. Один жадный скрипт способен исчерпать лимит для всех остальных.

Когда лимит упёрт — слепнет сам механизм: он перестаёт отличать «новых задач нет» от «трекер не ответил», и тихо простаивает или (хуже) действует по устаревшим данным.

Закладывайте это с первого дня: разумный интервал опроса (минуты, а не секунды), кэш последнего ответа с временем свежести, и дедупликация — не спрашивать трекер повторно про то, что уже спросили в этом же цикле.

5Правда и цифры

Уверенный неверный ответ дороже честного «не проверял» — на неверном ответе строят следующее решение, и ошибка множится.

Любое утверждение с числом — только проверенный факт с источником: документ, лог, команда и её вывод. Не проверил — не произносим ни число, ни причину.

Запрещены объяснения-догадки, выданные за факт: «вероятно, комиссия», «в пределах допуска», «округление», «расхождение между отчётами» — без предъявленной операции или строки-причины это не объяснение, а выдумка. Причины нет — так и говорим: «не установлено», и продолжаем искать, а не подставляем правдоподобную версию.

Благоприятный вывод («у нас всё хорошо», «риска нет») требует ТЕХ ЖЕ доказательств, что и тревожный, и обязан называть охват источника: за какой период и какой объём данных проверен. Отсутствие находки — не доказательство отсутствия: «не нашли» превращается в «нет» только когда проверено, что искали в правильном месте, за правильный период и с полным охватом источника.

6Проверка фактом

«Готово» на словах и «готово» на деле — разные вещи, и разницу видно только на прогоне, а не на глаз.

«Готово» произносится только после своей команды и её вывода — не по внешнему виду и не потому, что «так должно было сработать».

Эталон снимается ДО правки, на чистой главной линии кода. Без эталона «падения не связаны с моей правкой» — это догадка, а не факт: нужно сравнить списки того, что падало, до и после, а не полагаться на память.

Проверка обязана уметь ловить сам дефект: временно сломайте то, что проверяете — проверка обязана это заметить. Проверка, которая не краснеет ни от чего, не сторожит ничего, это просто фоновый шум.

Проверяет не тот, кто делал (см. правило 2), и закрытие идёт только по проверенному факту (правило 3) — оба правила именно об этом: о разнице между «должно работать» и «проверено, что работает».

7Параллельная работа

Одновременная работа над разными задачами экономит время — но только пока копии не начинают топтать друг друга или общий ресурс.

Разрешена при трёх условиях сразу: у каждой работы своя задача, своя изолированная копия кода, свой сторож.

Строго последовательны ровно два действия: прогон тестов на общей тестовой базе (параллельные прогоны дают разброс результата, и вывод о том, что именно сломалось, становится невозможным) и выкат в боевую среду — по одному, никогда одновременно.

8Сначала в архив, потом выкат

Обратный порядок — «выкатили, потом закоммитим» — это и есть источник расхождения между тем, что реально работает, и тем, что записано в истории изменений.

Одна дверь на боевую среду: до неё попадает только то, что прошло через архив (систему контроля версий). Ручных боевых правок в обход архива не бывает.

Метка происхождения: рабочий сервис умеет сказать, из какого именно снимка кода он собран, и честно отметить, если сборка была сделана с незакоммиченными правками.

Отдельный процесс постоянно сверяет боевую среду с архивом и сигналит не только о расхождении, но и о СВОЕЙ собственной поломке — если сверка замолчала, это не значит «всё совпадает».

Ветка, которая живёт только на диске и никуда не отправлена, — дыра в этой гарантии: она не защищена архивом. Перед удалением такой ветки — опись «ветка → контрольная точка → что в ней было → почему лишняя», закоммиченная ДО удаления, а не после.

9Ориентация перед работой

Папка на диске — не то же самое, что боевое состояние системы; работа, которая не знает, где она находится, почти всегда кончается лишней или ошибочной правкой.

Три команды перед любым словом о боевом состоянии:

  • Где я. На какой ветке стою и насколько она отстала от главной линии.
  • Что реально в бою. Сверка по СОДЕРЖИМОМУ — контрольная сумма ключевого файла, а не дата последнего коммита: дата ничего не доказывает.
  • Где ещё лежит этот код. Другие копии и ветки этого же репозитория, что в них трогали последним.

10Сторожа

Сторож, который сигналит неправильно, хуже отсутствующего — он создаёт ложное чувство защищённости именно там, где его больше всего ждут.

  • Fail-open. Поломка самого сторожа не останавливает работу человека — она только даёт сигнал о себе.
  • Сигнал привязан к «проблема жива», а не к «картина на экране изменилась». Иначе тихая, но всё ещё живая проблема пропадает из вида сама, без единого действия по её устранению.
  • Сторож обязан сигналить о собственной смерти. «Источник данных не ответил» — это не то же самое, что «проблем не найдено», и звучать это должно по-разному.
  • Ложная тревога дороже молчания. После ложной тревоги дежурство обычно снимают или перестают доверять каналу — и настоящую аварию потом никто не видит.

11Каналы сигналов

Если всё идёт в один поток, важное тонет в фоновом шуме, а фоновый шум раздражает, когда его путают с действительно важным.

Минимум два канала: личный канал того, кто принимает решения (туда — только то, что реально требует его внимания), и служебный канал механизма (всё остальное: «сторож упал», «слияние застряло», «лимит трекера исчерпан»). Не адресованное человеку идёт в служебный канал, даже если находка сама по себе интересная.

12Доставка задания агенту

Текст, набранный в поле ввода, — это ещё не отправленное сообщение; со стороны зависшая работа неотличима от работающей, пока кто-то не проверит буквально.

После текста задания — отдельное явное действие «отправить» (например нажатие Enter отдельной командой), и проверка, что поле ввода опустело и пошёл вывод. Сторож обязан сигналить, если в поле ввода долго висит неотправленный текст — это ловит и забытый ввод, и сообщение, адресованное не туда.

13Память и чекпойнты

Конец одного дела — момент, когда контекст либо сохраняется, либо теряется безвозвратно к следующему разу.

Дело закончилось или пройдена важная развилка — фиксируются ДВА разных документа:

  • Карта механики. Переживает конкретное дело: сроки, охват источников данных, грабли, куда смотреть в следующий раз.
  • Чекпойнт дела. Умирает вместе с делом: конкретные номера, даты, решения, что уже сделано именно в этот раз.

Смешивать их нельзя: карта механики, дополненная деталями одного конкретного дела, устареет вместе с этим делом и введёт в заблуждение следующего человека, который будет читать её уже без контекста.

Перед завершением сессии/захода: решения — в трекер, отработавшие копии кода — закрыть, следующий шаг назвать одной строкой.

14Уборка

Копия кода — расходный материал; забытая копия занимает место и иногда держит процессы, которые продолжают работать даже когда о них забыли.

Владелец уборки — правило/автоматика, а не память конкретного человека: «не забыть убрать» не работает как надёжный процесс.

Перед удалением любой копии — проверить: нет ли незакоммиченных правок, неучтённых файлов, коммитов, которых нет в архиве. Есть хоть что-то из этого — не удалять, вынести отдельным пунктом в список.

Пороги: свободное место на диске и число одновременно живых копий. Превышение порога — это сигнал, а не команда на автоматическое удаление без проверки выше.

15Секреты и доступы

Значение ключа, однажды попавшее в лог или в переписку, живёт там неопределённо долго — отозвать ключ куда проще, чем отозвать историю сообщений.

Значения секретов не печатаются НИКОГДА, даже «чтобы проверить, что всё в порядке». Проверяется факт наличия — задано значение или нет, — а не само содержимое.

Перед закрытием доступа, сменой ключа или ужесточением прав — поимённый список ВСЕХ, кто этим пользуется, особенно машинных потребителей (интеграции, автоматика, вебхуки) — их куда проще забыть, чем живого человека. Ключ без единого потребителя не перевыпускается заново «на всякий случай» — гасится совсем.

16Экономия

Расплывчатое задание «разберись и почини» стоит дороже точного задания с конкретным файлом и командой проверки — и в деньгах, и во времени ожидания.

  • Бюджет — часть самого задания: конкретная папка/файл вместо «разберись в теме», точечное чтение вместо чтения всего подряд, короткий отчёт без простыней логов.
  • Дешёвый факт добывается первым (быстрый прогон, точечный запрос) — и только то, на что он указал, разбирается дальше подробно и дорого.
  • Два отказа подряд — повод остановиться и разобраться в причине, а не повторять то же самое действие в третий раз в надежде на другой результат.
  • Мелкая точная правка достаётся более простому/дешёвому исполнителю; сложный разбор и итоговая проверка — более опытному.

17Отчёт владельцу/заказчику

Длинный отчёт с логами и техническими деталями читают по диагонали и пропускают именно то, что важно.

Три строки: что сделано · чем проверено · что осталось.

Строка «чем проверено» обязательна — именно её отсутствие выдаёт непроверенный вывод, даже если весь остальной текст звучит уверенно.

Если что-то нужно от заказчика/владельца — это отдельная явная строка в конце, а не растворённая где-то в середине текста фраза.

18Трекер ↔ среда разработки

Чтобы было понятно, где проходит граница между «трекер знает» и «работа пошла».

Событий из трекера не приходит. Ни вебхуков, ни подписок, ни слушающего адреса на нашей стороне. Всякое движение начинается с нашей стороны — кто-то спрашивает трекер, а не трекер сам сообщает нам о переменах.

Два способа спросить, и их не стоит путать.

  • По требованию. Среда разработки (или командная строка) идёт в трекер в тот момент, когда человек или агент попросил: прочитать задачу, сменить статус, прицепить ссылку на изменения. Авторизация делается один раз, ключ лежит локально на машине, а не передаётся заново с каждым запросом.
  • По расписанию. Свои короткие скрипты в системном планировщике задач двигают работу по стадиям без человека: частый интервал — минуты — для стадий «сдано → приёмка → вливание», редкий суточный прогон — для сводок и напоминаний о сроках.

Привязка задачи к работе. Рабочая копия кода создаётся одной командой и в момент создания связывается с номером задачи; исполнитель берёт бриф ИЗ ТЕЛА задачи, а не из переписки вокруг неё — отсюда требование писать тикет как самодостаточное ТЗ (раздел выше).

Цена опроса. У обращения к трекеру есть общий предел в единицу времени, который делят между собой все скрипты и все параллельные сессии сразу (раздел «Экономия» выше) — чем короче интервал опроса, тем быстрее упирается этот общий потолок, и тогда слепнет уже весь механизм, а не только та его часть, что опрашивала слишком часто.

Минимальный набор для повторения

Трекер с командным доступом (подойдёт и бесплатный, вплоть до системы задач при самом репозитории кода) · один токен доступа на машину · две строки в системном планировщике — частая для движения по стадиям и суточная для сводки и сроков · одна команда, поднимающая работу. Ни вебхуков, ни своего постоянно работающего сервера для этого не требуется.

2. newwork.sh
bash — одна команда поднимает работу по номеру задачи
#!/usr/bin/env bash
set -euo pipefail

# newwork.sh <номер-задачи>
#
# Поднимает свежую копию репозитория от origin/main через git worktree,
# заводит ветку с номером задачи и кладёт в копию бриф — текст задачи,
# который исполнитель прочитает как ТЗ (правило 1: агент читает тело
# задачи, а не переписку).
#
# Настройка под свой трекер — задайте TRACKER_FETCH, команду, которая
# печатает текст задачи по её номеру в stdout. Примеры:
#   export TRACKER_FETCH="gh issue view"                 # GitHub Issues
#   export TRACKER_FETCH="glab issue view"                # GitLab Issues
#   export TRACKER_FETCH="./task-from-file.sh tasks.md"   # свой список задач
#
# AGENT_LAUNCH (необязательно) — команда запуска исполнителя, получает
# путь к брифу последним аргументом. Не задано — копия просто готова,
# запускаете исполнителя сами.

TICKET_ID="${1:?укажите номер задачи: newwork.sh <номер>}"
: "${TRACKER_FETCH:?задайте TRACKER_FETCH — команда чтения задачи по номеру}"

REPO_ROOT="$(git rev-parse --show-toplevel)"
WORKTREE_DIR="${REPO_ROOT}/../work-${TICKET_ID}"
BRANCH="task/${TICKET_ID}"

git -C "$REPO_ROOT" fetch origin main
git -C "$REPO_ROOT" worktree add -b "$BRANCH" "$WORKTREE_DIR" origin/main

BRIEF_FILE="${WORKTREE_DIR}/BRIEF.md"
eval "$TRACKER_FETCH" "$TICKET_ID" > "$BRIEF_FILE"

echo "копия:  $WORKTREE_DIR"
echo "ветка:  $BRANCH"
echo "бриф:   $BRIEF_FILE"

if [ -n "${AGENT_LAUNCH:-}" ]; then
  ( cd "$WORKTREE_DIR" && eval "$AGENT_LAUNCH" "$BRIEF_FILE" )
fi
3. watch.sh
bash — простейший сторож: работа встала или отчиталась
#!/usr/bin/env bash
set -euo pipefail

# watch.sh
#
# Следит за признаком жизни работы (файл, который она обновляет по ходу
# дела) и зовёт команду оповещения, когда работа либо встала, либо
# отчиталась о готовности. Никаких готовых каналов внутри — оповещение
# задаётся снаружи через WATCH_NOTIFY.
#
# Настройка:
#   WATCH_TARGET    — путь к файлу с признаком жизни (его исполнитель
#                     обновляет сам по ходу работы, любым касанием mtime)
#   WATCH_NOTIFY     — команда оповещения; ей на вход придёт текст сообщения
#   WATCH_STALL_MIN  — сколько минут без изменений считать "встало" (по умолчанию 30)
#   WATCH_DONE_MARK  — строка-маркер готовности; если она есть в WATCH_TARGET,
#                      работа считается отчитавшейся, а не зависшей
#   WATCH_INTERVAL_SEC — пауза между проверками, секунд (по умолчанию 60)

: "${WATCH_TARGET:?задайте WATCH_TARGET — путь к файлу признака жизни}"
: "${WATCH_NOTIFY:?задайте WATCH_NOTIFY — команда оповещения}"
STALL_MIN="${WATCH_STALL_MIN:-30}"
DONE_MARK="${WATCH_DONE_MARK:-}"
INTERVAL="${WATCH_INTERVAL_SEC:-60}"

notify() { eval "$WATCH_NOTIFY" "\"$1\""; }

while true; do
  if [ ! -e "$WATCH_TARGET" ]; then
    sleep "$INTERVAL"
    continue
  fi

  if [ -n "$DONE_MARK" ] && grep -qF "$DONE_MARK" "$WATCH_TARGET" 2>/dev/null; then
    notify "готово: найден маркер завершения в $WATCH_TARGET"
    exit 0
  fi

  NOW=$(date +%s)
  MTIME=$(date -r "$WATCH_TARGET" +%s 2>/dev/null || echo "$NOW")
  IDLE_MIN=$(( (NOW - MTIME) / 60 ))

  if [ "$IDLE_MIN" -ge "$STALL_MIN" ]; then
    notify "работа не подаёт признаков жизни $IDLE_MIN мин (порог $STALL_MIN): $WATCH_TARGET"
    exit 1
  fi

  sleep "$INTERVAL"
done
4. Протокол приёмки
bash — машинные маркеры вердикта + правило «приёмщик код не правит»
#!/usr/bin/env bash
set -euo pipefail

# accept.sh
#
# Протокол приёмки на трёх машинных маркерах — принято / не принято /
# решает владелец. Вердикт пишется ОДНОЙ строкой в журнал приёмки,
# никогда в код проверяемой ветки.
#
# Правило: приёмщик код не правит. Нашёл дефект — вердикт REJECTED с
# причиной, а не молчаливое "заодно поправлю". Иначе приёмка перестаёт
# быть независимой проверкой и становится вторым автором.
#
# Формат строки вердикта:
#   <!-- verdict:ACCEPTED <ticket> <utc-iso8601> -->
#   <!-- verdict:REJECTED <ticket> <utc-iso8601> <причина одной строкой> -->
#   <!-- verdict:OWNER    <ticket> <utc-iso8601> <вопрос владельцу> -->
#
# VERDICT_LOG — файл, в который дописываются вердикты (общий журнал).

: "${VERDICT_LOG:?задайте VERDICT_LOG — файл журнала приёмки}"

verdict() {
  local kind="$1" ticket="$2" note="${3:-}"
  case "$kind" in
    ACCEPTED|REJECTED|OWNER) ;;
    *) echo "неизвестный вердикт: $kind (допустимо ACCEPTED/REJECTED/OWNER)" >&2; return 1 ;;
  esac
  printf '<!-- verdict:%s %s %s %s -->\n' \
    "$kind" "$ticket" "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$note" >> "$VERDICT_LOG"
}

# Последний вердикт по задаче — пусто, если приёмки ещё не было
last_verdict() {
  local ticket="$1"
  grep -F "verdict:" "$VERDICT_LOG" 2>/dev/null | grep -F " $ticket " | tail -n1 || true
}

# Пример использования:
#   verdict ACCEPTED TASK-1 ""
#   verdict REJECTED TASK-2 "признак закрытия не выполняется: команда падает"
#   verdict OWNER    TASK-3 "меняет договор с пользователем — нужно решение владельца"
#   last_verdict TASK-2
5. pre-push гейт
bash — тесты + сканер секретов перед пушем в защищённую ветку
#!/usr/bin/env bash
set -euo pipefail

# pre-push гейт: прогон тестов и грубый сканер секретов перед пушем
# в защищённую ветку. Кладётся в .git/hooks/pre-push (или вызывается
# из него отдельной командой).
#
# Настройка:
#   PROTECTED_BRANCH — какую ветку защищаем (по умолчанию main)
#   TEST_CMD          — команда прогона тестов; пусто — тесты пропускаются

PROTECTED_BRANCH="${PROTECTED_BRANCH:-main}"
TEST_CMD="${TEST_CMD:-}"
SECRET_PATTERN='(AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----|sk-[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{30,}|xox[baprs]-[A-Za-z0-9-]{10,})'

while read -r local_ref local_sha remote_ref remote_sha; do
  [ "$remote_ref" = "refs/heads/$PROTECTED_BRANCH" ] || continue
  [ "$local_sha" != "0000000000000000000000000000000000000000" ] || continue

  if [ -n "$TEST_CMD" ]; then
    echo "гейт: прогоняю тесты ($TEST_CMD)"
    if ! eval "$TEST_CMD"; then
      echo "гейт: тесты упали — пуш остановлен" >&2
      exit 1
    fi
  fi

  echo "гейт: сканирую секреты в диффе"
  BASE="$remote_sha"
  if [ "$remote_sha" = "0000000000000000000000000000000000000000" ]; then
    BASE=$(git rev-list --max-parents=0 "$local_sha" | tail -n1)
  fi
  if git diff "$BASE" "$local_sha" | grep -Eq "$SECRET_PATTERN"; then
    echo "гейт: похоже на секрет в диффе — пуш остановлен" >&2
    exit 1
  fi
done

exit 0

7. Сверка «бой ↔ архив»
bash — контрольная сумма боевого файла против архивной версии
#!/usr/bin/env bash
set -euo pipefail

# prod-check.sh <адрес-боевого-файла> <путь-к-архивной-копии>
#
# Скачивает ключевой файл с боевого адреса и сравнивает контрольную
# сумму с версией, лежащей в архиве (в git). Расхождение печатается
# явно, а не проглатывается молча — на нём ловится случай "в бою
# одно, в архиве другое", который иначе всплывает только на инциденте.

PROD_URL="${1:?укажите адрес боевого файла}"
ARCHIVE_PATH="${2:?укажите путь к файлу в архиве}"

PROD_SUM=$(curl -fsSL "$PROD_URL" | sha256sum | cut -d' ' -f1)
ARCHIVE_SUM=$(sha256sum "$ARCHIVE_PATH" | cut -d' ' -f1)

if [ "$PROD_SUM" = "$ARCHIVE_SUM" ]; then
  echo "совпадает: бой = архив ($PROD_SUM)"
  exit 0
else
  echo "РАСХОЖДЕНИЕ"
  echo "  бой:    $PROD_SUM"
  echo "  архив:  $ARCHIVE_SUM"
  exit 1
fi
8. Опись перед удалением ветки/копии
bash — обратимость удаления: сначала запись, потом снос
#!/usr/bin/env bash
set -euo pipefail

# pre-delete-inventory.sh <ветка> <файл-описи> ["почему лишняя"]
#
# Перед удалением ветки/рабочей копии записывает в файл описи
# "ветка -> контрольная точка -> что было -> почему лишняя" и требует,
# чтобы запись была закоммичена ДО удаления. Само удаление необратимо,
# опись — страховка на случай, если ветка понадобится снова.

BRANCH="${1:?укажите имя ветки}"
INVENTORY_FILE="${2:?укажите файл описи}"
REASON="${3:-не указана}"

SHA=$(git rev-parse "$BRANCH")
SUBJECT=$(git log -1 --format=%s "$BRANCH")

{
  echo "## $BRANCH"
  echo "- контрольная точка: $SHA"
  echo "- последний коммит: $SUBJECT"
  echo "- почему лишняя: $REASON"
  echo "- когда: $(date -u +%Y-%m-%dT%H:%M:%SZ)"
  echo
} >> "$INVENTORY_FILE"

git add "$INVENTORY_FILE"
if git diff --cached --quiet -- "$INVENTORY_FILE"; then
  echo "нечего коммитить — опись не изменилась" >&2
  exit 1
fi
git commit -m "опись перед удалением: $BRANCH"

echo "опись записана и закоммичена. теперь можно удалять:"
echo "  git branch -D $BRANCH"
echo "  git worktree remove <путь-копии>   # если была рабочая копия"
